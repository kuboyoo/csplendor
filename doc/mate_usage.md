# 詰み探索・証明・問題集生成

[README](../README.md)の詰み探索APIの補足です。以下のコマンドはリポジトリルートで実行します。

### C++ 解決器の探索方式

C++ の解決器（`solve_reveal_verified_mate_cpp`、`exact_mate_search`、`MateSearchSession`、
`solve_visible_only_winner_cpp`、準詰み）は、既定では深さ制限つきの深さ優先 AND/OR 探索（DFS）です。攻め側の節点は
1手でも証明できれば証明、守り側の節点とめくれは1つでも反例があれば反証です。置換表のキーは
「局面と残り攻め手数」で、未決着（予算切れ）は保存しません。反復深化は呼び出し側（深さ掃引）が行います。
`solve_reveal_verified_mate_cpp` と `search_reveal_verified_mate_depths` は `algorithm="dfpn"` で、同じ AND/OR グラフを
証明数・反証数で展開する df-pn を選べます（下の「df-pn（`algorithm="dfpn"`）」）。Python 版の df-pn は削除しました。

深さ（残り攻め手数）は、**攻め側の手番が終わる手**で1減ります。購入して貴族選択待ちや返却待ちに
入る手は手番の途中なので減らさず、その後の `VISIT_NOBLE` や返却で手番が終わったときに減らします。
探索本体、root の並列分割（`child_depth`）、`expand_mate_frontier` の `child_depth`、証明 DAG の
深さラベルと検証は、すべてこの規則に従います。

**最終手カット**: 最終ラウンドでない局面で攻め側の残りが1手のとき、攻め側が勝てるのはこの手番で15点に
届く場合だけです（15点未満で手番を渡すと、守り側の手で終局しても守り側の15点到達か引き分けで、攻め側の
勝ちにはならず、終局しなければ攻め側の手が残っていません）。そこで、この節点では手番の終わりに15点以上に
なる手（購入＋その後に取れる貴族、`VISIT_NOBLE`、すでに貴族の条件を満たしている場合のその他の手）だけを
展開し、そのような手が無ければ手を作らずに反証します。結果は厳密なままで、葉の層の展開がなくなるため、
同じ時間でおよそ1手深く読めます。めくれ検証の解決器（`solve_reveal_verified_mate_cpp` と、それを使う
深さ掃引・`MateSearchSession`・`exact_mate_search`・`root_mate_probe`）、visible-only の候補探索、準詰み
（残り1手で15点に届かなければ勝率0）に入っています。

**blank 意味論（公開札だけの探索）**: `exact_reveal_search=False` の探索（深さ掃引・`MateSearchSession` の anytime
探索・`root_mate_probe` の手順 4 の正の証明、`expand_mate_frontier` と root 分割の子の評価）は、めくれを列挙しません。
補充された枡は blank（どの未知の札でもありうる枡）になり、守り側は blank の枡がある段の「未知で未取得の札」
（探索開始時に山札にあり、まだ場・予約・購入済みのどこにもない札）をどれでも購入・予約できます（oracle 手）。
攻め側は blank の枡を使えません。山札の配列は、補充・oracle 手・山札予約のたびに1枚消費し、枚数は常に実際の山札と
同じです。山札予約の候補は配列に残る札ではなく、その段の未知で未取得の札すべて（blank の枡に消費された札を含む）
で、配列にない候補は山札の一番上と入れ替えてから予約します。2026-11-07 までは消費された札が候補から落ち、
oracle 手が山札を消費していませんでした（P3）。

**oracle 予約の重複除去**: 守り側の oracle 予約（blank の枡の未知の札 c の予約）は、その段の山札が空でないときは
生成しません。守り側の山札予約（`RESERVE_DECK`）は「その段の未知で未取得の札すべて」を候補にする AND 節点で、
候補 c の子局面は oracle 予約 c の子局面と blank 意味論で同じだからです（守り側が c を持ち、金1枚を得て、山札が
1枚減り、blank の枡はそのまま。11枚を超えた返却はどちらも同じ `RETURN_GEM` の決定）。両者は山札の配列から
どの札が消えたかだけが異なりますが、blank 局面の意味（整合する実際の局面の集合）は公開札・blank の枡・山札の
枚数・取得済みの未知の札の集合だけで決まり、配列の中身には依存しません。したがって山札予約の候補 c が PROVEN
なら oracle 予約 c に整合する実際の局面もすべて攻め側の勝ちで、上の支配の帰納法（T の守り側の手が S の検証済みの
手に写る）はそのまま成り立ちます。山札が空のときは山札予約が合法でないので oracle 予約を従来どおり生成し、
oracle 購入には対応する手がないので常に生成します。2026-11-07 までは両方を生成し、置換表のキーが配列の中身
（unseen）を含むため同じ部分木を2回探索していました（BENCH 局面の blank 探索・深さ4 で生成した手の 55% が
oracle 予約）。

**同型の札によるまとめ**: めくれと山札予約の候補は `card_equivalence_class`（段・点・ボーナス・費用が同じ札）
ごとに代表1枚だけ調べます。同型の札 c, c' を入れ替える写像は規則の自己同型（勝敗・合法性に関わる性質が全て
同じ）なので、代表の子局面の証明を入れ替えて写せば他方の証明になり、今後のめくれ・山札予約の候補集合も
入れ替えで対応します。ただし標準の 90 枚にはこの意味で同型の札が無い（40/30/20 枚が全て別の同値類）ため、
このまとめは実際には何も減らしません。oracle 手を同型でまとめる案（2026-11-07）も同じ理由で効果が無く、入れて
いません。

**blank 意味論の支配**: blank 局面 S と、S の blank の枡と山札に具体的な札を当てた実際の局面 T を考えます。
S で攻め側が合法な手は T でも合法で、結果は再び対応します（公開札の購入・予約、トークン、貴族、返却は同じ盤面の
操作。補充は S では枡が blank になり山札が1枚減り、T では山札の1枚が枡に出る。山札予約は枚数が同じなので合法性が
一致し、S の候補「未知で未取得の札」は T の山札を含む）。T で守り側が合法な手は S にも対応する手があります
（T で見えている未知の札の購入・予約は oracle 手、山札予約は候補に含まれ、それ以外は同じ操作）。終局・最終ラウンド・
深さ・最終手カットの判定は両方に共通の値（点、購入枚数、手番、公開札）だけで決まります。したがって木の高さに
ついての帰納法で、**S が PROVEN なら T も PROVEN** です（攻め側の証明手は T でも使え、T の守り側のどの手も S で
検証済みの手に写る）。逆は成り立たず、S の反証・未決は T について何も言いません。

**blank 支配カット**: 厳密探索（`exact_reveal_search=True`）のめくれ節点（公開札の購入・予約で山札から補充が起こる
手）では、まず最初の具体めくれ（最も危険と推定した札）を厳密に調べ、それが証明できたら、残りのめくれをまとめて
blank の子局面（補充を blank にした局面）で1回探索します。blank の子が PROVEN なら上の支配により残りの全ての
めくれが PROVEN なので、列挙を省きます。blank の子が反証・未決なら残りを従来どおり具体的に列挙します。最初の
めくれが反証なら blank は試さないので、攻め手の反証の費用は従来と同じです。blank の探索は厳密探索とは別の置換表
（blank の局面のキー）を使い、探索ごとに捨てます（`MateSearchSession` が持ち越すのは厳密表だけ）。主手順は最初の
具体めくれを通るので途切れません。証明 DAG・frontier・root 分割・準詰みは全めくれを具体的に列挙する経路なので
カットを使いません。統計は `blank_cut_attempts`（blank を試した回数）と `blank_cut_proofs`（省けた回数）です。

**守り側の最終応手カット**: 最終ラウンドでない局面で守り側の手番、攻め側の残りが1手（守り側の応手のあと攻め側が1手
指して終わり）、守り側に貴族選択・返却の決定が残っていない節点では、守り側がどう応じても攻め側が次の手番で勝つことを
応手を作らずに判定し、成り立てば節点を PROVEN にする。判定は次の量だけで決まり、どれも守り側の1手で変わらない
攻め側の持ち物（トークン・ボーナス・予約札・点）と、守り側の1手で起こりうる変化の上界から計算する。

1. **攻め側の購入候補**: 攻め側の予約札と公開札のうち、攻め側が今のトークンで買える札 c。守り側の1手は攻め側のトークン・
   ボーナス・予約札を変えないので、守り側の応手のあとも c は買える（公開札 c を守り側が購入・予約で取った場合を除く）。
   手番の終わりの点 S(c) = 攻め側の点 + c の点 + **保証された貴族**。保証された貴族は、c を買ったあとの攻め側のボーナスで
   条件を満たす盤上の貴族のうち最高点のもの。ただしその貴族を守り側がこの手番で取れる（守り側の今のボーナス、または
   守り側が今買える札1枚のボーナスを加えたボーナスで条件を満たす）なら2番目の貴族の点とする（守り側は1手番に貴族を
   1人しか取れない）。
2. **保証された点 S\***: 守り側の1手は公開札を高々1枚しか取り除けない（購入か予約の1枚）。よって S\* = max(守り側が
   取り除けない候補の S(c) の最大値, 全候補の S(c) の2番目の値)。公開札 c を守り側が取り除けるのは、守り側が予約できる
   （予約枠が空いている）か c を買えるとき。予約札は取り除けない。S\* < 15 なら判定は不成立。
3. **守り側の1手の到達点 D1**: 守り側が今買える札（公開札・自分の予約札・blank 探索では blank の枡がある段の未知で
   未取得の札）それぞれについて 守り側の点 + 札の点 + 新しいボーナスで取れる最高の貴族、および購入しない場合の 点 +
   今取れる最高の貴族、の最大値。
4. **勝敗の比較**:
   - 攻め側が後手（P1）のとき: 守り側の手のあと攻め側が 15 点以上で手番を終えると、その手番でラウンドが完了して終局する
     （守り側が先に 15 点に届いていても同じ）。S\* > D1 なら攻め側の勝ち（同点の枚数判定は使わず、厳密な不等号を要求する）。
   - 攻め側が先手（P0）のとき: D1 ≥ 15 なら守り側の応手でラウンドが完了して終局し守り側が勝ちうるので不成立。そうでなければ
     攻め側の手で最終ラウンドに入り、守り側がもう1手指して終局する。守り側の2手の到達点の上界 D2 を、次の各場合の
     点 + 札の点 + **最終ボーナスで条件を満たす貴族の上位2人の点の和**（1手番に1人、2手番で2人）の最大値とする。
     2手目に買える札 y は、公開札と自分の予約札に加えて、**補充が起こった段の未知の札**（厳密探索では各段の山札の配列、
     blank 探索では山札が空でないか blank の枡がある段の未知で未取得の札）。補充が起こる段は、守り側の1手目が公開札の
     購入・予約（oracle 購入を含む）ならその段、および攻め側の勝つ購入が公開札ならその段（15 点に届く公開札の段すべて）。
     (a) 今買える札 x を金を温存する支払いで買い、残りのトークンと増えたボーナスで y を買う。(b) トークン取得のあと y を買う。
     取得は銀行を無視して「不足している色それぞれ 1 枚（3 色まで）か、1 色 2 枚」のどちらか大きい方だけ不足を減らすとする
     （守り側の補充は無い）。(c) 予約（公開札でも山札でも）のあと金 1 枚ぶんの不足まで許して y を買う。予約した札自身が y に
     なりうるので、この場合の y は全段の未知の札を含む。(d) 何も買わない。S\* > D2 なら攻め側の勝ち。

**健全性**: 守り側の1手が盤面に与える変化は、公開札1枚の除去と補充（またはめくれ）、山札1枚の消費、銀行のトークンの増減、
貴族1人の取得、守り側自身の点・ボーナス・トークン・予約札の変化だけで、攻め側の持ち物には触れない。したがって守り側の
どの応手（厳密探索の全めくれ、blank 探索の oracle 手を含む）のあとも、攻め側には S\* 以上で手番を終える購入が残っている
（2 の議論）。終局の判定は点と購入枚数だけで決まり、守り側の到達点は D1・D2 がそれぞれ上界なので、4 の不等式が
成り立てば攻め側の勝ちが確定する。D1・D2 は守り側の手の選択肢の上位集合（銀行を無視したトークン取得、補充が起こりうる段の
全未知札、貴族2人、10 枚制限の無視）で計算した上界なので、判定の成立は厳密な PROVEN と一致し、不成立は何も言わない
（通常の展開に戻る）。15 点に届く購入の
ない節点（最終手カットで子が全て反証される節点）は 1 の候補が空で即座に不成立になり、費用は最終手カットの判定と同程度。

適用範囲: めくれ検証の解決器（厳密探索・blank 探索、`MateSearchSession`・深さ掃引・`exact_mate_search`・
`root_mate_probe`）。準詰み（確率）、visible-only の候補探索、証明 DAG・frontier・root 分割の展開経路は従来どおり
全応手を列挙する。証明 DAG は、このカットで証明された節点（手を持たない PROVEN の置換表の項）に出会うと守り側の全応手を
列挙して子を個別に証明する。主手順は、カットで証明された守り側の節点では通常の順序で最初の合法手（めくれは山札の一番上）
を代表として進み、その先の攻め側の節点（カットで探索されていない）は一時的な表に数ノードだけ探索して続ける（探索が
残した置換表・その参照順・統計は変えないので、session の持ち越しと切り詰め、`nodes` の意味は従来どおり）。統計は `last_reply_cut_attempts`
（判定した節点）と `last_reply_cut_proofs`（証明した節点）。

**最終手の直接生成**: 最終手カットの節点（最終ラウンドでない局面で攻め側の手番、残り1手）は、2026-11-07 までは全合法手

（上の層ごとの内訳）。絞った結果は「手番の終わりに 15 点以上になる購入」の全支払いパターンだけなので、それを直接作る
（`winning_last_move_codes`、`src/solver_win_threshold.h`）。候補は攻め側の予約札と公開札のうち `score_after_purchase` が
15 以上の札で、支払いパターンの列挙は合法手生成と同じ `MoveGenerator::emit_card_purchases`（`simple_payment_mode` も同じ値）
を使う。したがって作られる手の集合は「全手を作って絞る」結果と同一で、手の並べ替えは手の鍵（種類・点・pack 値）で決まるので
順序も同一である。例外として、貴族選択待ち・返却待ちの節点と、攻め側がすでに盤上の貴族の条件を満たしていて購入以外の手でも
15 点に届く節点（`VISIT_NOBLE`・返却・トークン取得なども残る）は、従来どおり全手を作って絞る。合法手生成の上限
（`MAX_MOVES` = 2048 手）はこの節点では届かないので、絞る前の生成が打ち切られることはない。適用先はめくれ検証の解決器
（厳密探索・blank 探索）と準詰み。visible-only の候補探索は手を代表でまとめる別の生成を使うので従来どおり絞る。
結果（判定・証明 DAG・主手順・ノード数・`legal_moves`）は変わらず、時間だけが変わる。

**最終ラウンドの直接判定の前置き**: 攻め側の最終手のあとの守り側の節点（最終ラウンド、P1 の手番、保留の決定なし。上の層ごとの
内訳で時間の 23%）は、守り側の全手の到達点（購入ごとの点と購入枚数、購入以外の手の点）から勝敗を直接決める
`resolve_final_round_direct` でほぼ全て決まる。この判定は盤面だけから数十回の比較で済むので、2026-11-07 からは局面のハッシュの
計算・置換表の参照・経路（繰り返し）の確認より前に行い、決まった節点は置換表に保存せずに返す。保存の費用（約 90 バイトの項の
挿入）と表の占有（上限での flush が有用な項を消す）の方が判定より高く、再訪問時も判定し直す方が安い。直接判定で決まらない
最終ラウンドの節点（守り側に貴族選択や返却が続く手がある場合など）は従来どおりハッシュ・置換表のあとで全手を展開し、保存する。
結果（判定・主手順・証明 DAG）は同じで、`memoized_states` と `memo_hits` が減る。ノード数は置換表の flush が起こらない限り同じ
（直接判定の節点はハッシュの前でも `nodes` に数える）。証明 DAG（`build_proof_node`）と frontier（`expand_frontier_node`）は、
置換表に項のない最終ラウンドの節点を直接判定で確かめてから従来どおり全応手を展開する。主手順は従来も最終ラウンドの節点で
止まるので変わらない。

**攻め側の2手の到達上界による反証（reach cut）**: 最終ラウンドでない局面で攻め側の手番、攻め側の残りが2手、貴族選択・返却の
決定が残っていない節点では、攻め側が自分の2手番で到達できる点の上界 U を計算し、U < 15 なら手を作らずに REFUTED にする
（`reach_cut_applies` / `attacker_may_reach_win_in_two_moves`、`src/solver_win_threshold.h`）。U は守り側の最終応手カットの
D2 と同じ関数 `two_move_reach_at_least` を攻め側に適用したもので、次の各場合の 点 + 札の点 + **最終ボーナスで条件を満たす
貴族の上位2人の点の和** の最大値である。(a) 今買える札 x（公開札・自分の予約札）を金を温存する支払いで買い、残りのトークンと
増えたボーナスで y を買う。(b) トークン取得（銀行を無視して「不足している色それぞれ 1 枚（3 色まで）か 1 色 2 枚」の大きい方）
のあと y を買う。(c) 予約（公開札でも山札でも、金 1 枚）のあと金 1 枚ぶんの不足まで許して y を買う（予約した札自身も y に
なりうる）。(d) 何も買わない。y の候補は公開札・自分の予約札と**全段の未知の札**（厳密探索では各段の山札の配列、blank 探索では
山札が空でないか blank の枡がある段の未知で未取得の札。どの段も補充が起こりうるものとして扱う）。

健全性: 攻め側の点は自分の手番でしか増えず、1 手番に高々 1 枚の購入と 1 人の貴族で増える。守り側の応手は攻め側のトークン・
ボーナス・予約札・点を変えず、盤面には公開札 1 枚の除去と補充（またはめくれ）・山札 1 枚の消費・銀行の増減・貴族 1 人の取得しか
起こさない。補充・めくれで現れうる札は全段の未知の札として y の候補に含めてあり、守り側が取り除いた札を候補から外していないので、
守り側のどの応手のあとでも攻め側の 2 手目の選択肢は (a)〜(d) の候補集合に含まれる。各場合の到達は銀行・10 枚制限・補充の段・
取得の合法性を無視した上界（「守り側の最終応手カット」の D2 の議論と同じ）なので、U は攻め側の 2 手番後の点の上界である。
最終ラウンドでない局面で攻め側が 2 手以内に勝つには 2 手目の手番の終わりに 15 点以上が必要（最終手カットと同じ: 15 点未満で
手番を渡しても、守り側の手で終局すれば守り側の 15 点到達か引き分けで攻め側の勝ちにならず、終局しなければ攻め側の手が残らない）。
したがって U < 15 なら REFUTED は厳密で、不成立（U ≥ 15）は何も言わず通常の展開に戻る。反証だけを足すので、PROVEN の集合・
証明 DAG・主手順は変わらない（反証された部分木を省く分だけノード数・統計が変わる）。統計は `reach_cut_refutations`（反証した
節点）。適用先はめくれ検証の解決器（厳密探索・blank 探索）。準詰み・visible-only は従来どおり。

計測（2026-11-07、1 スレッド、置換表 200万件、8c16782 との比較）: ランダム終盤（seeds 2000〜2099 を 9〜12 点まで進めた
局面 × 攻め側 2 × exact/blank × 深さ 1〜3、ノード上限 15万、1,164 ケース）で合計ノード 130.4万 → 84.0万（exact 深さ2 で 66%、
深さ3 で 71%、blank 深さ2 で 55%、深さ3 で 54%）、以前からの 360 ケースで 40.2万 → 23.8万。判定の食い違いなし、詰みの

ほぼ変わらず、深さ5 は 240 秒では未決のまま。層ごとの内訳（深さ5 を 30 秒）では、攻め側 d=2 の節点 24.8万のうち反証は 258

の開番地法への置き換えと、守り側 d=1 の応手を購入・予約・取得の順に遅延生成すること（どちらも結果を変えない）。

**置換表の開番地法化**: めくれ検証の解決器の置換表（blank 探索の `memo_` と厳密探索の `exact_memo_`）は、2026-11-07 までは
`std::unordered_map`（項ごとに malloc する連鎖法。参照は バケット配列 → 節点 → 鍵の比較と 2〜3 回の飛び先の読み込み、保存は
malloc、flush は全節点の free）で、深さ5 の時間の約 2 割を占めていた。これを線形探査の開番地法（`src/solver_flat_table.h`、
`FlatMemoTable`）に置き換えた。1 スロット = 鍵 + 項 = 64 バイト（1 キャッシュライン）で、残り攻め手数は鍵の metadata 語の
上位 8 ビットに `depth + 1` として入れる（0 が空スロット。鍵の型 `RevealDepthStateKey` / `RevealExactDepthStateKey` は
`depth()` と `empty()` を持つ）。項の `action_count` は 32 ビット。blank の鍵 48 + 項 16、厳密の鍵 32 + 項 32。容量は 2 の冪に
限らず（添字は `mix(hash) * 容量` の上位語）、負荷率の上限は 0.7。上限 `max_memo_states` が N のとき容量は
C = `ceil(N / 0.7)` を超えず、`C >> k`（k ≥ 3）の列で倍々に伸びて C/8 から C へ跳ぶ（1024 スロットから。再ハッシュは
旧配列と新配列が同時に生きるので、大きな表を写す再ハッシュを C/8 からの 1 回に限る）ため、N 件を再ハッシュなしで保持でき、
N = 200万で 2,857,143 スロット = 183 MB（1 件あたり 91 バイト）。表の型は上限なし（N = 0）なら 2 の冪で倍々に伸びるが、探索は常に正の N を渡す（「探索のメモリ予算」）。
探索の最初にノード上限から表を予約する処理（`reserve_active_memo`）はやめた（開番地法の成長は安く、並列分割の枝ごとに
183 MB を先に割り当てないため）。
削除（session の `trim_exact_cache` と制限つき探索後の反証の除去）は後方シフト（backward-shift）で、墓標を使わない。
flush は全スロットの初期化 1 回。表の中身・探索の結果（判定・証明 DAG・主手順・ノード数・`memoized_states`）は変わらず、
`memo_hits` の意味も同じ。並列分割の枝ごとの表も同じ型なので、合計は N × スレッド数 × 91 バイト以下。

計測（2026-11-07、1 スレッド、置換表 200万件、69bd2fb との比較。共有マシンの負荷を避けるためノード数で予算を揃えた
CPU 時間）: BENCH 厳密探索の深さ4（148.5万ノード）が 1.42 → 1.38 秒、深さ5 の 3,000万ノードが 28.98 → 25.44 秒（−12%）。
判定・主手順・ノード数・`memo_hits`・`memoized_states` はすべて同一（ランダム終盤 3,024 ケースでも同一）。メモリは、深さ5 を
2,500万ノード走らせて厳密・blank の両表を上限まで埋めたときの RSS のピークの増分が、証明の移植の表（`line_proofs_` /
`line_refutations_`、上限なし）を切った条件で 406 MB → 379 MB、既定（移植あり）で 533 MB → 583 MB。2 表の定常は
2 × 183 = 366 MB（unordered_map は約 406 MB）で、ピークは最後の再ハッシュ（C/8 + C）を含む。移植ありのピークが増えたのは、
移植の表（16 バイトのスロット、負荷 0.5 で 2 の冪に倍々、上限なし。BENCH 深さ5 の 2,500万ノードで 128 MB）の倍化
（旧 64 MB + 新 128 MB が同時に生きる）が、早く上限の容量に達する新しい置換表と重なるためで、置換表そのものの使用量は
減っている（移植の表の上限は次の段落）。

**移植の表の上限**: 証明の移植の表（`line_proofs_` / `line_refutations_`、`src/solver_line_table.h` の `LineTable`）は、
16 バイトのスロット（鍵 = 攻め手順のハッシュ、値 = 手）の線形探査の表で、2026-11-07 までは上限なしに負荷 0.5 で 2 の冪に
倍化していた。これに上限を付けた。容量は 65,536 スロットから倍々に伸び、置換表の上限（探索の開始時に決めた件数）が N のとき
`max(65536, bit_floor(N))` スロット（N = 200万で 1,048,576 スロット = 16 MB、2 表で 32 MB）で止まる。探査は家（home）から
8 スロットの窓に限り、窓に同じ鍵も空きもなければ、上限の前なら倍化し、上限では家のスロットを新しい項で上書きする。
表は手の順序付けにだけ使うので、上書きで消えた項は「その攻め手順で移植の手を最初に試さない」だけで、判定・証明は
厳密なまま（ノード数は変わりうる）。上限に達するまでは中身が上限なしの表と同じなので、ノード数も同じ。倍化の一時領域
（旧 + 新）は最大 8 + 16 = 24 MB。計測（2026-11-07、BENCH 厳密探索の深さ5 を 2,500万ノード、置換表 200万件）: RSS のピークの
増分は 69bd2fb の 527 MB、上限なしの移植の表（7fe35bc〜c1909c9）の 583 MB に対して 395 MB。深さ3・4（1.1万・148.5万ノード）は
上限に届かず、ノード数・`memo_hits`・`memoized_states` は同一。

**守り側の応手の遅延生成**: 守り側の節点はたいてい最初の 1〜2 手で反証される（上の層ごとの内訳）が、2026-11-07 までは
全合法手（平均 27〜30 手、トークン取得は返却の組み合わせで増える）を作ってから並べていた。手の並び順は `ordered_action` の
rank（0 購入・貴族、1 公開札の予約、2 トークン取得、9 山札予約など）が第 1 キーなので、全手の並びは rank ごとの並びの
連結である。そこで守り側の節点（貴族選択・返却待ちでなく、順序表 `order_hints` がなく、トークンが 10 枚以下）では、
`LazyReplies`（`src/reveal_verified_solver.cpp`）が rank の群を 購入（blank 探索の oracle 購入を含む）→ 公開札の予約（oracle
予約を含む）→ トークン取得 → 山札予約 の順に、必要になった群だけ `MoveGenerator::emit_purchase_codes` /
`emit_reserve_visible_codes` / `emit_take_codes` / `emit_reserve_deck_codes`（`src/move_generator.h`、合法手生成と同じ列挙）で
作り、群ごとに全手と同じ比較で並べ替える。反証が購入で見つかれば取得は作らない。証明の移植（`line_refutations_`）と
反復深化の順序付け（浅い深さの厳密表の反証手）は、記憶した手の群だけを作って合法性を確かめ、全手の並びと同じ順
（移植の手、反復深化の手、残りを並び順に）で訪問する。したがって訪問順・判定・証明 DAG・ノード数は全手を作る場合と同一である。
置換表の項の `action_count`（主手順の各手に出る「その局面の合法手数」）は、反証が最後の群より前に見つかった節点では
作っていないので、項に「未集計」の印（flag bit 4、`action_count_deferred`）を付け、主手順を作るときにその局面で全手を
作って数える（結果の `line` は従来と同一）。全群を訪問した（証明された）節点では群の合計を入れる。合法手生成の上限
`MAX_MOVES`（2048）に届きうる局面（購入の手が 1368 を超える。トークン 10 枚以下なら取得は 665 手以下、公開札の予約は 15
手以下）、守り側に手がなく `PASS` だけの局面、順序表のある探索は従来の全手生成に戻る。変わる統計は `legal_moves`
（作った手の数。遅延で減る）と、作らなかった oracle 手の `oracle_purchase_actions` / `oracle_reserve_actions` だけで、
`line_order_hits` / `iterative_order_hits` は全手の並びでの判定（手が 2 つ以上あり、先頭でない）を再現する。
適用先はめくれ検証の解決器の探索本体（厳密・blank）。最終ラウンドの展開、証明 DAG・frontier・主手順の展開、準詰み、
visible-only は従来どおり全手を作る。

計測（2026-11-07、1 スレッド、置換表 200万件、開番地法の置換表との比較、ノード数で予算を揃えた CPU 時間）: BENCH 厳密探索の
深さ4 が 1.38 → 1.29 秒、深さ5 の 3,000万ノードが 25.44 → 24.70 秒（69bd2fb からは −15%）、生成した手（`legal_moves`）が
深さ4 で 1,057万 → 601万、深さ5 の 3,000万ノードで 1.39億 → 1.05億。守り側の節点の多くは最終応手カットか最初の購入で
決まり、取得の生成はもとから少ない層（守り側 d=1 の生成は時間の 8%）だったので、効果はその範囲にとどまる。
ランダム終盤（seeds 0〜59・2000〜2099・3000〜3099、exact/blank × 攻め側 2 × 深さ 1〜3、3,024 ケース）で判定・主手順・
ノード数・`memo_hits` は 69bd2fb と同一で、違うのは `legal_moves` だけ（1,168 ケースで減少）。

**df-pn（`algorithm="dfpn"`）**: `solve_reveal_verified_mate_cpp(..., algorithm="dfpn", dfpn_table_bytes=...)` と
`search_reveal_verified_mate_depths(..., algorithm="dfpn")` は、上の DFS と同じ AND/OR グラフ（手の生成・絞り込み・
順序、めくれ、深さ、各カット）を証明数・反証数で展開する（`src/dfpn_mate_solver.h`、[設計](mate_dfpn_cpp_design.md)）。
既定は `"dfs"` のままで、結果の形・判定・主手順と証明 DAG の意味は同じ。

- **めくれ**: 補充の起こる手は「最初の具体めくれ c0、blank の子 B、休眠の残り」を子にする。B は c0 が証明されてから
  blank の DFS で決着まで探索し、証明されれば残りを省き（blank 支配カット）、そうでなければ残りを起こして具体的に探索する。
  山札予約は候補札の AND。blank 探索では oracle 手を守り側の手に加える。
- **深さ**: 鍵は DFS と同じ「局面と残り攻め手数」で、(局面, 残り) のグラフは DAG なので経路の繰り返しの確認は要らない。
  残り攻め手数 1 以下の節点（攻め側の最終手と、その前の守り側の手）は DFS（`forced_win_with_memo`）で決める。
- **置換表とメモリ**: 決着した節点は DFS と同じ exact/blank の表（`max_memo_states`、flush）に DFS と同じ項で入れるので、
  主手順・証明 DAG・session の持ち越しは DFS のコードがそのまま扱う。未決着の (pn, dn, work) は容量固定の df-pn 表
  （`dfpn_table_bytes`、既定 128 MiB。4 スロットの組で、満杯なら work 最小を置換）にだけ置き、予算を超えて割り当てない。
- **カット**: 終局・最終ラウンドの直接判定・最終ラウンドの展開・最終手カット（直接生成）・reach cut・最終応手カット・
  blank 支配カット・証明の移植と反復深化の順序は DFS の関数をそのまま呼ぶ。未訪問の兄弟は、探索した兄弟（未決着）の
  pn・dn の最大値で見積もる。
- 統計に `dfpn_expansions`、`dfpn_table_stores`、`dfpn_table_replacements`、`dfpn_table_bytes` が加わる（DFS では 0）。

計測（2026-11-07、1 スレッド、置換表 200万件、DFS との比較。時間比 = DFS / df-pn で、1 より大きいと df-pn が速い）:
ランダム終盤（seeds 0〜59・2000〜2099・3000〜3099 を点数 7〜13 まで乱数で進めた局面 × 攻め側 2 × exact/blank × 深さ 1〜4、
深さ4 は 20 秒上限、4,016 ケース）で判定の食い違い 0、未決 0（両方）。詰みのある局面の合計時間は exact 深さ3 が 0.91 → 1.16 秒
（0.79）、深さ4 が 10.86 → 12.47 秒（0.87）、blank 深さ3 が 0.65、深さ4 が 0.72。その深さで初めて詰む局面（深さ4 で 22 局面）は
exact 0.84、blank 0.73、不詰みは exact 深さ4 で 0.81、blank 0.64。10 ms 以上かかった深さ4 の詰み 60 局面（exact）のうち
df-pn が速いのは 5 局面。BENCH の exact は深さ3 が 0.009 → 0.011 秒、深さ4 が 1.14 → 1.57 秒（ともに不詰み）、深さ5 は
240 秒で両方とも未決（2.95億 / 2.84億ノード）。BENCH の blank 深さ5 は両方とも詰みを証明し、60.2 → 102.8 秒。
df-pn は DFS の順序（購入優先、証明の移植、反復深化）に近い順で読み、1 節点の費用（守り側の全手の生成、再訪のたびの
手の生成し直し）の分だけ遅い。したがって既定は DFS のままとする。


`scripts/dfpn_mate_solver.py` は、任意局面から player0 または player1 の強制勝利を探索します。

公開カードだけで候補手順を高速探索し、その後に未公開カードのめくれ、相手の全応手、全支払いパターン、局面入力後の山札予約結果を C++ の解決器で検証します（めくれ検証）。めくれ検証では visible-only の最短主手順 prefix を固定して先に厳密検証し、証明できなかった場合は固定範囲を緩め、最後に通常の幅広い検証へ戻ります。

```bash
python scripts/dfpn_mate_solver.py \
  --position 'bank:... | visible:... | decks:... | nobles:... | P0:... | P1:... | 0' \
  --attacker 0 \
  --time-limit 30 \
  --pretty
```

完全な詰み応手を確認する場合は、証明に関係する局面だけを DAG 形式で出力できます。同一局面はノード ID で共有されるため、木を単純展開するよりメモリ使用量を抑えられます。

```bash
python scripts/dfpn_mate_solver.py \
  --position '...' \
  --attacker 0 \
  --reveal-proof-dag \
  --proof-dag-format compact \
  --proof-dag-node-limit 100000 \
  --proof-dag-edge-limit 500000 \
  --time-limit 30
```

証明 DAG は `proof_tree.verification.proof_dag` に返ります。攻撃側は証明に採用した手、守備側は全合法応手、山札予約は全ドロー結果を保持します。既定の `compact` 形式では、同じ action/child に進む複数の具体めくれカードをカードID bitset の reveal group としてまとめ、edge は action template と reveal group への参照で保存します。具体カード集合は保持するため、全めくれに対する応手情報は失いません。従来の辞書型 DAG が必要な場合は `--proof-dag-format v1`、比較用に両方出す場合は `--proof-dag-format both` を指定します。complete DAG は返却前に全 edge を合法手として再走査し、検査済みなら `validated: true` になります。上限超過時も詰み判定結果は維持し、DAG のみ破棄して理由を返します。

完全DAGが大きすぎる場合は、`csplendor.expand_mate_frontier()` で現在局面の1層だけを検証・展開できます。攻撃側ノードでは証明手1手の全めくれ、守備側ノードでは全合法手の全めくれを返します。各 edge の `child_state` は、SPNに含まれない終局・最終ラウンド・貴族選択待ち・予約後の返却待ちも保持する版付きスナップショットです。予約後の返却は予約手の一部で、詰み深さを消費しません。次の呼び出しでは `load_mate_frontier_game(state=...)` で復元します。

```python
import csplendor as cs

game = cs.load_mate_frontier_game(position=position)
frontier = cs.expand_mate_frontier(game, attacker=1, depth=5)
edge = frontier["edges"][0]
child = cs.load_mate_frontier_game(state=edge["child_state"])
next_frontier = cs.expand_mate_frontier(
    child,
    attacker=1,
    depth=edge["child_depth"],
)
```

深さを1手ずつ増やして最初の詰みを調べる場合は
`cs.search_reveal_verified_mate_depths()` を使います。不詰みを確定した深さだけを
通過し、詰み、`Unknown`、累積予算、または最大深さで停止します。
終局済みの非勝利局面、または残る全カード・貴族の点を攻撃側が独占しても15点に
届かない局面では、深さに依存しない `permanent_no_mate` 証明で直ちに停止します。

```python
depth_search = cs.search_reveal_verified_mate_depths(
    game,
    attacker=1,
    min_depth=5,
    max_depth=8,
    max_nodes=10_000_000,
    time_limit_seconds=120,
)
```

実戦AIでは、同一対局中に1個の `MateSearchSession` を保持します。`search_anytime()`
は浅い深さが未確定でも次へ進み、正の詰み証明だけを返すため、持ち時間内の着手
選択に向いています。anytime探索中も一部のCPU予算で厳密置換表を育て、次の深さ
では浅い証明手・反例手を合法手順序へ反映します。相手応手後の局面が前手番の表に
あれば、同じ深さの結果は1ノードの参照で再利用されます。

```python
session = cs.MateSearchSession(
    attacker=ai_player,
    jobs=16,
    max_cache_states=2_000_000,
)

result = session.search_anytime(
    game,
    min_depth=1,
    max_depth=8,
    time_limit_seconds=2.0,
)
if result["status"] == "mate":
    action = cs.Action.unpack(result["winning_root_action"])
    # 通常のAI候補より優先して、この検証済み着手を選択する

# 対局終了・別対局開始時だけ破棄する
session.clear()
```

最短手数まで保証する解析用途では `session.search()` または
`search_reveal_verified_mate_depths()` を使います。こちらは各N手不詰みを全合法手・
具体的めくれについて確定してからN+1へ進むため、実戦向けより高コストです。
思考時間を外部から打ち切る場合は `session.cancel()` を別スレッドから呼べます。

### root の詰みの探り（`root_mate_probe`、2026-10-05 追加）

AI が手を選ぶ前に root で詰みを探る処理を、C++ の1関数 `root_mate_probe`
（`src/root_mate_probe.h`）にまとめています。Python と WASM（embind）の両方から同じ結果で
呼べるよう、スレッドと Python に依存しません。1回の呼び出しで完結し、対局をまたぐキャッシュは
持ちません。

```python
config = cs.RootMateProbeConfig()          # 既定値は下表
result = cs.root_mate_probe(game, config, previous_value=0.72, time_limit_seconds=0.3)
if result.proven:
    action = cs.Action.unpack(result.action_code)   # result.action_id は V5 の行動ID
```

手順（攻め方 = 手番のプレイヤー）:

1. **発火**: `enabled` で、攻め方の点数が `min_points` 以上、または `previous_value`
   （攻め方の前回の手番の root 評価値）が `trigger_value` 以上なら探る。評価値で発火したとき
   `value_triggered` が真になる。`trigger_value` が未設定（`None`）なら点数だけで決める。
2. **非公開の予約**: 相手が非公開の予約札を持つ局面は探らない（ソルバーが札を見てしまうため）。
   `stop_reason = "opponent_hidden_reserve"`。
3. **予算**: 攻め方の点数が `endgame_points` 以上、または評価値で発火したら「終盤」で、
   `endgame_max_nodes`・`endgame_time_limit_ms` を使う。それ以外は `max_nodes`・`time_limit_ms`。
   引数 `time_limit_seconds` を渡すと、選んだ時間上限を上書きする。0 は上限なし。
4. **探り**: 深さ `min_depth`〜`max_depth` を浅い順に、正の詰み証明だけを探す
   （`MateSearchSession.search_anytime` と同じ予算配分。各深さは残り予算を残りの深さ数で割った分を使い、
   その 1/4 までを置換表の温め（`warm_start_nodes`・`warm_start_time_ms` が上限）に使う）。
   `warm_start_time_ms = 0` は温め独自の時間上限を設けないだけで、時間上限があればその 1/4 で打ち切る。
   下位の探索には 0（無制限）を渡さず、共有の締め切りの残りから正の時間を渡す。
5. **終盤の厳密探索**: 4 で詰みが出ず「終盤」なら、深さ 1〜`endgame_exact_depth` を攻め方の全手・
   具体的なめくれで調べる（`search_reveal_verified_mate_depths` と同じ）。ノード上限は選んだ予算、
   時間は **4 と共有する1つの締め切りの残り** で、残りが無ければ実行しない。
   したがって呼び出し全体が時間上限を超えない。
6. **結果**: 詰みなら `value_proven`。root の手が特定できれば `proven` と `action_code`・`action_id`
   を返す。手のない証明は `stop_reason = "mate_proven_without_root_action"`。

| 設定 | 既定 | 結果 | 内容 |
|---|---|---|---|
| `enabled` | `True` | `attempted` | 探索したか |
| `min_points` | 9 | `proven` | root の手まで特定した詰みか |
| `trigger_value` | `0.6`（`None` 可） | `value_proven` | 詰み（手の有無を問わない） |
| `endgame_points` | 10 | `depth` | 詰みの深さ（攻め方の手数。無ければ -1） |
| `max_nodes` / `time_limit_ms` | 20,000 / 20 | `action_code` / `action_id` | 詰みの初手（pack 値 / V5 の行動ID。無ければ -1） |
| `endgame_max_nodes` / `endgame_time_limit_ms` | 2,000,000 / 150 | `nodes` / `elapsed_ms` | 4 と 5 の合計 |
| `min_depth` / `max_depth` | 1 / 3 | `stop_reason` | 停止理由（探らなかった場合は空文字列） |
| `endgame_exact_depth` | 2 | `value_triggered` | 評価値で発火したか |
| `max_cache_states` | 50,000 | | |
| `warm_start_nodes` / `warm_start_time_ms` | 50,000 / 50 | | |
| `memory_budget_bytes` | 0（自動。「探索のメモリ予算」） | | |

ノード上限だけで打ち切る条件（時間上限 0）では、新しい `MateSearchSession(jobs=1)` を使った
dlsplendor の `RootMateSearch.probe` と、状態・深さ・手・停止理由・ノード数が一致します。
時間で打ち切る条件では、5 の時間を共有の締め切りの残りにしている分だけ結果が異なり得ます。

### 厳密な詰みの深さ探索（`exact_mate_search`、2026-10-11 追加）

`search_reveal_verified_mate_depths(jobs=1)` の深さ探索を、C++ の `exact_mate_search`
（`src/exact_mate_search.h`）としても公開しています。WASM から呼ぶためのもので、シングルスレッドで
Python に依存しません。`root_mate_probe` の終盤の厳密探索もこの関数です。

- 深さ `min_depth`〜`max_depth` を浅い順に、攻め方の全手と具体的なめくれで調べる。ノード数と時間は
  全深さの累計で、各深さは残りを使う。
- 詰みなら停止し、その深さの主手順 `line`（`action_code`、`reveal_card`、`action_count`）を返す。
  反証できた深さは `verified_no_mate_through_depth` を進めて次の深さへ。予算切れ・未決着なら停止する。
- 最初に、攻め方が二度と勝てないことの安価な証明（終局済みで攻め方の負け、または得点上限が15未満）を
  確かめ、あれば `status = "permanent_no_mate"`（`stop_reason` は証明の種類）で終える。
- 結果の `status` は `mate` / `no_mate_within_max_depth` / `unknown` / `permanent_no_mate`、
  `stop_reason` は `mate_proven` / `max_depth_reached` / `cumulative node limit exceeded` /
  `cumulative time limit exceeded` / ソルバーの未決着理由 / 証明の種類で、Python 版と同じ文字列。
  `mate_depth`・`verified_no_mate_through_depth`（無ければ -1）、`winning_root_action`（pack 値）と
  `winning_root_action_id`（V5。無ければ -1）、`nodes`、`elapsed_ms` も返す。
- 設定 `ExactMateSearchConfig` は `attacker`、`min_depth`、`max_depth`、`max_nodes`、`time_limit_seconds`、
  `max_memo_states`、`memory_budget_bytes`（「探索のメモリ予算」）を持つ。証明DAG・`required_root_action`・順序表・並列化は扱わない（Python 版を使う）。

### 外部評価による手の順序表と探り（2026-10-02 追加）

`MateOrderHints` は「局面ハッシュ → 手番側の手（pack code、良い順）」の表です。局面の
キーは `Board.set_deck_search_hash()`（山札を集合として扱う規則ハッシュ）で、解決器が置換表に
使う値と同じです。表にある局面では手をその順で試し（表にない手は従来の順序で後ろに続く）、
ない局面は従来どおりです。`solve_reveal_verified_mate_cpp`、`search_reveal_verified_mate_depths`、
`search_reveal_verified_mate_anytime`、`NativeMateSearchSession.search` の `order_hints=` に渡し、
並列分割の各枝にも同じ表が渡ります。統計には `hint_lookups` / `hint_hits` が加わります。

```python
import numpy as np
hints = cs.MateOrderHints(
    np.asarray(keys, dtype=np.uint64),      # 局面ハッシュ
    np.asarray(offsets, dtype=np.int64),    # len(keys) + 1
    np.asarray(codes, dtype=np.uint64),     # 連結した pack code
    attacker_restrict_top_k=0,
)
result = cs.search_reveal_verified_mate_depths(game, attacker=1, min_depth=1, max_depth=6,
                                               time_limit_seconds=60, jobs=8, order_hints=hints)
```

順序だけの表は結果の厳密性を変えません（攻め側は最初の勝ち手で、守り側は最初の反例で枝を
閉じるため、良い順序は証明を速くし、不詰みの証明は速くなりません）。

`attacker_restrict_top_k = k`（k > 0）にすると、表にある攻め側の局面では表の先頭 k 手だけを
試します（**探り**）。見つかった詰みは守り手とめくれを全て検証した正しい証明ですが、見つからない
ことは不詰みの証明になりません。`search_reveal_verified_mate_depths` はこのとき各深さを
`inconclusive` として次の深さへ進み、結果の `exact` は False、`restricted_probe` は True、
`verified_no_mate_through_depth` は進みません。`solve_reveal_verified_mate_cpp` に
`exhaustive_attacker_actions=True` とともに渡すと拒否されます。
表は dlsplendor の方策網から `dlsplendor.evaluation.mate_hints.build_mate_order_hints` で作れます
（根から数手ぶんの局面をめくれごとに展開して一括評価）。

計測（dlsplendor `doc/native_v3_search_20260929.md`、2026-10-02）では、順序だけの表に効果はなく、探りは
3 手詰めの局面でノード数を半減させた程度でした。解決器の律速は守り側の応手×めくれの分岐で、攻め側の
順序付けでは到達深さは伸びません。既定では無効（`order_hints` を渡したときだけ有効）です。

### 証明の移植、no-take 探り、置換表の上限（2026-10-02 追加）

- **証明の移植（`line_transplant=True`、既定で有効）**: 攻め側の節点を証明した手を「そこまでの攻め側の
  手順のハッシュ」で記憶し、同じ攻め手順で到達した節点（めくれ違い・守り手違いの兄弟）で最初に試します。
  守り側の反例手も同様に記憶します。順序付けだけなので結果は厳密なままです。統計 `line_order_hits`。
  `line_transplant=False` で従来の順序に戻せます。
- **no-take 探り（`no_take_probe=True`）**: 攻め側はトークンを取らず、守り側の購入は同じカードについて
  最も金を使わない支払いだけを試します（攻め側が銀行を使わない前提では、金を手元に残す支払いが他の
  支払いを支配するため）。見つかった詰みは正しい証明、失敗は不詰みの証明になりません
  （`exhaustive_attacker_actions=True` と併用すると拒否、深さ掃引では `restricted_probe` 扱い）。
- **制限つき探索と置換表**: 攻め手を削る設定（`no_take_probe=True`、`attacker_restrict_top_k > 0` の
  順序表、`required_root_action`、候補手順の prefix 固定）の下での反証は不詰みの証明ではありません。
  反証はその探索の中でだけ使います。探索をまたいで置換表を持ち越す `NativeMateSearchSession` で攻め手を
  削れるのは `no_take_probe` と `attacker_restrict_top_k` だけで（`required_root_action` と prefix 固定は
  毎回解除される）、これらを使った探索が終わった時点で反証を表から除き、証明だけを残します。したがって
  制限つきの探索の後に全手の探索をしても、詰みを見逃しません。
- **置換表の上限（`max_memo_states=N`）**: 表が N 件に達すると空にして詰め直します（結果は厳密のまま、
  直近の局面を再探索する分だけ遅くなる）。表は開番地法（上の「置換表の開番地法化」）で 1 件あたり 91 バイト
  （64 バイトのスロット、負荷率 0.7）、6 スレッドの並列分割では枝ごとに表を持ちます。既定の 0 は
  「自動」で、探索の開始時に端末の空きメモリから N を決めます（次の「探索のメモリ予算」）。正の N を
  渡すとそのまま使います（無制限はありません。大きな N を渡します）。
  `NativeMateSearchSession` が持ち越す表（`max_cache_states`）は、探索の前に N の半分以下に
  切り詰めます。持ち越した表が上限ちょうどだと、次の探索の最初の保存で全部消えてしまうためです。

### 探索のメモリ予算（2026-11-07 追加）

詰み探索・準詰み・visible-only の表の上限は、探索の開始時に1回だけ、端末の空きメモリから決めます
（`src/solver_memory_budget.h`。探索の途中では変えないので、1回の探索の中で上限が揺れることはありません）。

1. **空きメモリ**（`available_memory_bytes()`、取れなければ 0）: Linux は `/proc/meminfo` の `MemAvailable` と、
   cgroup v2 の自分と祖先の `memory.max − memory.current`（上限のあるもの）の最小。macOS は `host_statistics64` の
   空き・非活性・パージ可能なページ。Windows は `GlobalMemoryStatusEx` の `ullAvailPhys`。WASM（`__EMSCRIPTEN__`）は
   常に 0（ブラウザ側でしか分からない）。
2. **予算**（`solver_memory_budget_bytes(available_bytes, jobs)`）: 空きメモリの 1/4 を 64 MiB〜2 GiB に挟み、
   並列のジョブ数で割る。共有マシンで学習が並走しても足りるよう保守的にしている。空きメモリが 0（取れない）なら
   既定の 512,000,000 バイト（200万件。2026-11-07 までの固定の既定 `DEFAULT_MAX_MEMO_STATES` と同じ）をジョブ数で割る。
   WASM の既定は 256 MiB（100万件。線形メモリの上限 2 GiB（`MAXIMUM_MEMORY` の既定）に網・探索木と並んで収まる）。
3. **件数**（`resolve_max_memo_states(max_memo_states, memory_budget_bytes, jobs)`）: 正の `max_memo_states` は
   そのまま返す。0 なら予算（`memory_budget_bytes` が正ならそれをジョブ数で割った値、0 なら 2 の予算）を
   1 件あたり 256 バイトで割った件数。256 バイトは、厳密と blank の 2 表の定常（2 × 91）、最後の再ハッシュの一時領域
   （C/8）、2 つの移植の表（各 `bit_floor(N)` スロット × 16 バイトと倍化の一時領域）の合計の上界。準詰みの
   `prob_memo_` と visible-only の 3 表も同じ件数で flush する。

| 呼び出し | 決める場所 | jobs |
|---|---|---|
| `search_reveal_verified_mate_depths` / `search_reveal_verified_mate_anytime` | 関数の開始時（全深さ・全枝で同じ N） | 引数 `jobs` |
| `MateSearchSession.search` / `search_anytime` | 呼び出しの開始時 | `MateSearchSession(jobs=...)` |
| `near_mate_search` / `search_near_mate`、`exact_mate_search`、`root_mate_probe` | 関数の開始時（設定の `memory_budget_bytes`） | 1 |
| `solve_reveal_verified_mate_cpp` などの1回の探索、`NativeMateSearchSession.search`、`solve_visible_only_winner_cpp` | 探索の開始時 | 1 |

WASM では、JS 側が `navigator.deviceMemory`（GB、丸めた値）などから予算を決め、`RootMateProbeConfig`・
`NearMateSearchConfig`・`ExactMateSearchConfig` の `memory_budget_bytes` に渡します（0 は上の WASM の既定）。
表は使った分だけ伸びるので、上限は確保量ではありません。ノード上限の小さい探索（`root_mate_probe` の 2万ノード
など）は、上限によらずノード数以下の件数しか使いません。`root_mate_probe` の終盤の厳密探索は、ノード上限があるときは
件数をノード上限以下にします。

計測（2026-11-07、1 スレッド、69bd2fb との比較。空きメモリ 32 GiB の共有マシンで自動の件数は 8,388,608 件 = 予算 2 GiB）:
ランダム終盤 3,024 ケース（seeds 0〜59、2000〜2099、3000〜3099、ノード上限 15万・40万）は判定・主手順・ノード数・`memo_hits`・
`memoized_states` がすべて同一（違うのは遅延生成による `legal_moves` だけ）。BENCH 厳密探索の深さ3（11,535 ノード）・深さ4
（148.5万ノード、1.72 → 1.37 秒）はノード数・`memo_hits` が同一。深さ5 の 3,000万ノードは CPU 時間が 28.6 秒（200万件、flush 6 回）
→ 23.5 秒（200万件を明示）/ 24.8 秒（自動、flush 1 回）。深さ5 の 2,500万ノードの RSS のピークの増分は 527 MB（69bd2fb）
→ 395 MB（200万件を明示）/ 1,724 MB（自動、終了時 749万件。予算 2 GiB の内）。

計測（dlsplendor `doc/native_v3_search_20260929.md` 参照）: 3 手詰めの局面で証明の移植はノード数を
1,989 万 → 424 万（4.7 分の 1）、時間を 4.8 秒 → 2.8 秒にした。実対局の終盤 81 局面（深さ 1〜4 の掃引、
20 秒）では合計ノード 22.7 億 → 18.9 億（−17%）、詰み発見 36 → 37 局面。no-take 探りの追加効果はわずか
（守り側の分岐の大半はトークンの取り・返却で、支払い方の統合では減らない）。

### 準詰み（確率的な詰み判定、2026-10-02 追加）

`near_mate_probability_cpp(game, attacker, depth, ...)` は「攻め側が自分の手 `depth` 手以内に勝ちを強制できる
確率」の下限を返します。木は厳密詰み探索と同じで、攻め側は最大、守り側は最小（最善の守り）、めくれは
その段の未見カードの一様分布で平均します（同スペックのカードは枚数で重み付け）。葉は終局の事実だけで、
網の評価値は使いません。値 1.0 が厳密な詰みです。

`required_root_action`（packed action code、既定は指定なし）を渡すと、攻め側の初手をその手だけに限って評価します
（`root_actions` もその1手だけ）。探索で選んだ手の準詰みの確率を確かめる用途（dlsplendor の準詰みによる手の
上書き）に使います。合法手でない code は `ValueError` です。

値そのものを厳密に出すには木全体が必要なので、`search_near_mate` は閾値の問い合わせで挟み込みます。
窓 `(T - eps, T)` で呼ぶと「確率 T 以上で勝ちを強制できるか」を、詰み探索と同じ打ち切り（守り手の 1 つ、
または反例のめくれの合計が確率を T 未満に押し下げた時点で節点を閉じる）で答えます。閾値 1.0 → 0.9 →
0.75 → 0.5 の順に試し、証明できた閾値が下限（`lower`、`lower_depth`、`best_action_usi`、反例のめくれ
`losing_reveals`）、反証できた閾値が上限（`upper`、その深さ `upper_depth`）になります。下限は深さに
ついて単調で、上限は判定が完了した最も深い深さのものです。

```python
near = cs.search_near_mate(game, attacker=1, min_depth=1, max_depth=3,
                           thresholds=(1.0, 0.9, 0.75), time_limit_seconds=20,
                           max_memo_states=30_000_000)
# near["lower"] = 0.9, near["upper"] = 1.0, near["lower_depth"] = 2,
# near["losing_reveals"] = [{"card": 5, "weight": 1, "value": 0.0}, ...]
```

挟み込みの本体は C++ の `near_mate_search`（`src/near_mate_probe.h`、2026-10-11）で、Python の
`search_near_mate` はその薄いラッパーです（返す辞書の形式 `NEAR_MATE_FORMAT` は同じ）。シングルスレッドで
Python に依存しないので、WASM（embind）からも同じ結果で呼べます。C++ の設定 `NearMateSearchConfig` は
`attacker`、`min_depth`、`max_depth`、`thresholds`（既定 1.0/0.9/0.75/0.5。高い順に並べ替え、重複は除く）、
`max_nodes`、`time_limit_seconds`（全問い合わせの累計）、`no_take_probe`、`line_transplant`、`max_memo_states`、
`memory_budget_bytes`（「探索のメモリ予算」）を持ちます。`no_take_probe=True` で閾値を満たせなかった問い合わせは、省いた手があるので反証にならず、
`verdict` は `inconclusive` で上限を下げません（下の閾値と次の深さは続けて試し、詰みが出なければ
`stop_reason` は `restricted_probe_exhausted`）。root も他の節点と同じ終局・深さの判定に従い、終局済みなら攻め方の勝ちで 1、それ以外で 0、
攻め方の手番で深さ 0 なら 0 です。結果 `NearMateSearchResult` は `lower`/`upper`、`lower_depth`/`upper_depth`（無ければ -1）、
深さごとの区間 `bounds`（`depth`、`lower`、`upper`、`decided`）、`best_action`（pack 値）と `best_action_id`
（V5 の行動ID。無ければ -1）、最善手のめくれ `best_action_reveals`（Python の `losing_reveals` は値が 1 未満の
ものだけ）、`root_actions`、`undecided`、`stop_reason`、`attempts`（`depth`、`threshold`、`verdict`、`nodes`、
`elapsed_ms`、`unknown_reason`）、`nodes`、`elapsed_ms` です。手順・停止理由の文字列は Python 版と同じです。

費用: 閾値 1.0 は詰み探索と同じ（3 手詰めの局面で約 3 秒）。閾値を下げるほど打ち切りが弱くなり、
深さ 2 では数秒、深さ 3 では値が 1 に近い場合以外は 30 秒以内に決まらないことが多い（2026-10-01 の対局の
終盤で計測）。`no_take_probe`、`line_transplant`、`max_memo_states`、`order_hints` は詰み探索と同じ意味です。
攻め側の制限は下限の正しさを保ちます。splendorgui の詰み判定は、厳密な詰みがないときに深さ 3 まで
（閾値 1.0/0.9/0.75、制限時間の 4 割）を自動で追加し、「準詰み: 2手以内の強制勝ち確率 90%以上（手）/
外れめくれ: C5, C14」または「準詰みなし: 2手以内の強制勝ち確率は 75%未満」と表示します。

確認用の主手順を `splendorgui` で再生する場合は、`--kifu-output mate.kifu` を追加します。検証済みの主手順（C++ の `line`）を Splendor KIFU として保存し、具体的なめくれは棋譜コメントの `reveal:C<id>` 注釈で残します。`splendorgui` が読む `strategy.json` は `scripts/generate_mate_puzzles.py` が問題ごとに保存します（下の「詰め問題集の生成」）。

`--simple-payment` を指定すると、購入時の支払いをゴールド温存パターンに限定できます。完全検証が必要な場合は指定しないでください。

### 詰め問題集の生成

`scripts/generate_mate_puzzles.py` は、csplendor だけで動くランダム対局（`scripts/puzzle_engine_adapter.py` の `RandomPurchasePlayer`。購入手があれば購入手から、なければ全合法手から一様に選ぶ）から終盤局面を生成し、めくれまで検証済みの詰みだけを問題集として保存します。ランダムに選んだ終盤開始手数に到達した後は、詰みが初めて見つかるまで1手番ごとに候補局面を検証します。対局中だけ簡易支払いモードを有効にします。対局は `--seed` で再現できます。詰み検証では通常支払いモードに戻し、購入時の全支払いパターン、局面入力後の山札予約、めくれを検証します。

```bash
python scripts/generate_mate_puzzles.py \
  --output-dir generated/mate_puzzles \
  --count 100 \
  --max-attempts 10000 \
  --min-depth 5 \
  --max-depth 7 \
  --no-strategy-dag \
  --mate-jobs 16 \
  --uniqueness-jobs 16 \
  --time-limit 30
```

進捗は attempt 開始と詰み探索開始時に表示されます。`--min-losing-alternatives` を1以上にした場合は誤答側詰み探索も表示されます。棄却時は `stage=rejected`、棄却理由、完全な SPN `position` を表示します。対局中の定期表示間隔は `--progress-seconds` で変更できます。

高コストなめくれ検証の前に、点差、合法手数、両者の楽観的な近未来得点、visible-only 探索で候補を絞ります。既定では両者が3手以内に15点へ到達しうる合法手12個以上の局面を対象とし、depth 3以上の詰みだけを採用します。詰み証明後は全合法初手を固定して再検証し、別解がない問題だけを保存します。条件は `--threat-turns`、`--min-legal-actions`、`--min-optimistic-score`、`--min-depth`、`--visible-prefilter-time-limit`、`--uniqueness-time-limit` で調整できます。`--uniqueness-max-depth 8` のように指定すると、各初手を問題の詰み深さから指定深さまで反復深化し、より長い別解も除外します。各初手では最初の `--uniqueness-positive-time-limit` 秒（既定2秒）で別解の正証明を高速に探し、残りの累積予算で全合法手・具体的めくれの不詰みを厳密検証します。各初手の累積予算は `--uniqueness-node-limit` と `--uniqueness-time-limit`、候補局面・誤答側の詰み探索は `--mate-jobs 16`、初手間のCPU並列数は `--uniqueness-jobs 16`（いずれも `0` は論理CPU数）で指定します。誤答時に相手の詰みまで成立することは既定の採用条件ではありません。必要なら `--min-losing-alternatives 1` 以上を指定します。

生成物は `depth_XX/<問題ID>/` に分類されます。`XX` はソルバー上の攻撃側手数深さです。各問題には局面情報 `problem.json`、検証済み代表手順 `answer.kifu`、代表手順とDAG状態を収める `strategy.json` が含まれます。DAG作成を有効にした場合は、攻撃側の証明手、守備側の全合法応手、公開カード補充と山札予約を含む全めくれ結果を保持し、同一局面をノードIDで共有します。既定ではDAG作成を試みますが、ノード・辺上限を超えても詰み判定と代表手順が検証済みなら保存します。完全DAGを必須にする場合は `--require-complete-dag`、DAG作成を省いて生成を優先する場合は `--no-strategy-dag` を指定します。DAGの有無と省略理由は `problem.json` の `strategy_dag` および `quality` に保存されます。`strategy.json` は既定で compact DAG を保存し、めくれカード集合は reveal group の bitset として厳密に残します。従来形式が必要な場合は生成時に `--strategy-dag-format v1`、比較用に両方残す場合は `--strategy-dag-format both` を指定します。めくれ候補は現在の山札だけから取り、同じレベル・点数・ボーナス・コストのカードは同型として代表だけを検証します。公開カード補充は一度 blank として進めた局面から反例になりやすい reveal を推定し、危険度の高い候補から検証します。非公開カードを即購入・即予約する oracle 手は合法手順DAGには出力されません。再現性を保つため、生成物内の SPN は伏せ予約カードを `?C<id>` 形式で保存します。通常の公開用 SPN における `?L<level>` と異なり、伏せ予約であることと実カードIDの両方を保持します。購入済みカードは `bought:[<id>,...]`、取得済み貴族は player section の `nobles:[<id>,...]` に保存します。
