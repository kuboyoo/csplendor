# 3D-1 事前計画・復元契約（2026-09-05）

基準は採用済み3D-P2 `ef312a15f451d566c428ce7b955a788ede6c533c`。
source digestは `8c402dfd467ec18944c0541eb2ec3191e0ba8a99a393818b7d0895221d983611`。
専用branch/worktree `perf/solver-normal-rollback` / `csplendor-normal-rollback`。
元repoとP2 worktreeのユーザー変更を持ち込まない。記録はdoc下へ保存する。

既存UndoRecordは通常applyの診断用で、solverへの採用は未完了。capture/restoreを再利用し、
新しい汎用Board表現は作らない。3Bのfull Board＋sidecar guardは任意めくれ・oracleのreferenceとして
残す。公開Game::undo、MCTS、3D-2の任意deck patchは対象外。

## 実装と復元対象

| 対象 | 保存・復元契約 |
|---|---|
| Board bank / visible | 全要素のold value |
| acting player gems/bonuses/points | 全scalar/array。packed_gems/packed_bonuses/noble maskもraw値を戻す |
| reserved / hidden / reserved_count / purchased_count | 全slot・countを保存。予約購入のshiftも戻す |
| purchased_cards / acquired_nobles | old sizeを保存、append-only前提を検査してtruncate。既存prefixは変えない |
| 相手player | 通常Game applyは変更しない。再帰子のguardが例外時も自身の変更を戻す。oracleで両player全fieldを比較 |
| decks | 通常Game applyは高々1山のtopをpop。countとold topを保存。子の復元がinactive slotを保証しなくても外側のpopped cardを戻せる |
| nobles | countと配列を保存し、有効順序も復元 |
| current_player / turn / final_round / waiting_noble / winner | 全てold valueを保存 |
| cached_hash / hash_valid | valid/invalidともraw値を復元。RuleMutatorがcommit/破棄された後に外側guardが戻す |
| Game modes | blank_refill / simple_paymentをscope内で復元 |
| Game history / board_history | apply_trusted(false)のみ。触らない、返却データは独立所有 |
| 3B sidecar | remaining_by_level/all, acquired_hidden, claimed, rule/deck hash, activeを既存コピーで一括復元 |
| 3C TT / stats / limits / root / P2 scratch | branch rollback対象外。既存寿命・trim・UNKNOWN・cache契約を維持 |

適用先はvisible-onlyの代表手生成・bounded探索・minimax、およびreveal solverの通常Game apply経路。
任意めくれ/予約oracleは既存full snapshotを維持。未検証editor/不適合入力はfull snapshotへfallback。
restoreはnoexcept・確保不要、apply=false/throw/early return/limit/cancelでも動作する。
copy失敗時はmutation開始前に伝播し、例外をREFUTEDに変換しない。

相手playerを保存しない根拠は `Game::apply_unchecked_with_mutator` の通常switchから
`apply_take_gems`、reserve、purchase、noble visit、`finish_standard_action` を追った結果による。
資源・購入・貴族の更新は全て遷移開始時の `board.current_player` のみ。`end_turn` と
`check_game_end` は両者の値を参照するが、変更するのは手番・turn・final_round・winnerだけ。
PASSはcopyを使うが、同じend_turnとwinner設定のみ。再帰先では、その時点のacting playerを
別guardが保存・復元する。editorによる割込み書換え・公開undoはこの前提に含めない。

RuleMutatorは `Game::apply_trusted` 内の自動変数であり、成功return・false・例外のいずれも
外側rollbackの前に寿命が終わる。未commitのdestructorはhash candidateを公開しない。
公開Game undoのfull Board historyは変更しない。VERIFY時だけcommitのnoexceptを外して
前後へ例外を注入する（Releaseでは従来のnoexceptと命令列、hook/TLSなし）。

## 事前固定の採否・検証

- primary: visible_solver / five_moves / fixed100k nodes（通常着手復元が直接の対象）。
  正式22pairsと独立holdoutで5%以上のE2E改善、CI下端>1を目安。
- secondary/guards: exact_reveal hidden_reserve d7/1M、d3、warm、forced-pass長経路、
  editor、proof on/off、逆手番。2%超の退行はCIと独立再測定で判断。
- 基準はP2の未変更build/3dp2-release。Release/portable、VERIFY/PERF OFFで測定。
  既存paired runner、CPU4、22pairs/11blocks、2warmups、fixed inode回転、bootstrap10000。
- 同じstatus/UNKNOWN、nodes/legal/terminal/memo/persistent/保持TT、主手順、ordered action/reveal、
  proof/frontier semantic digestを必須とする。allocation/rollback実装counterは同一性gateではない。
- parent/childの全field・active deck順・provenance内容・hash validity/raw cache・sidecarをoracle照合。
  支払い途中、provenance append後、source除去、貴族処理、hash commit前後、visitorで失敗注入。
- normal/simple payment、全ActionType、貴族待ち、予約shift、0/1枚山、入れ子、中断後再開を確認。
- 小unit→smoke→formal/holdout→全native/Python、既知5/7手、ASan/UBSanとoracle。
  performance counters unavailableならN/A、システム権限を変更しない。

未改善なら本番prototypeを撤去し、実験記録・棄却理由を残す。次Phaseへ自動では進まない。
変更をレビューし、日本語commit・作業branchへの通常pushで終了する。

## 限定再測定の追加（初回全体テスト後・追加測定前）

単発のshallow/proofでは初回とholdoutが揺れ、既存native 2000回集約のproof on/offも
中央値0.984/0.986倍、95% CI下端0.975/0.974で2% gateをまだ確定できない。
初回の結果は全て保存し、同じbinaryの独立holdoutをproof on/off各66pairs（33blocks）で
一度追加する。初回に約9%の低下が出たshallowも同じ既存集約器で22pairs測る。
集約器は各callでfresh solverを作り、native solve timerを合算するP2の既存adapter。
本番core static libraryのSHA一致を要求し、別driverのcode layoutと単発との差は別記する。
2%の基準を緩めず、追加holdoutのCI下端>=0.98を要求する。満たせなければ
問題経路の修正または採用範囲の縮小を行い、同じbinaryを際限なく再測定しない。

## 初期案の棄却と探索本体への限定

追加native proof-onは0.98081倍、CI [0.97775,0.98341]で上記gate未達。
初期案をそのまま採用しない。source/diffは `raw/phase3d1/prototype_v1_sources.json.gz` に保存した。

この低下をcompact restore命令そのものの費用とは断定できない。code layout/stack frame等の

実探索途中からのcancel→再開もテストする。

2%の非劣性はまだ確定しないので、v1と同じ事前固定の独立66pairsをon/off各一度だけ追加し、
