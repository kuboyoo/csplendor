## 24.2 仮説

### 計測前の仮説

1. trusted apply 後の exact/observable hash 全再計算が MCTS の主要固定費である。
2. exact reveal の state key は全board field、山札、購入履歴を毎node走査している。
3. solverの枝ごとの `Board` copy/restoreと可変長container allocationが支配的である。
4. shared-tree MCTSでは edge検索、共有atomic、reservation、lockが並列scaleを制限する。
5. legal codeのcount前走査と合法手生成の再帰がrule-engine hot pathである。
6. solver TT のkey比較・probeが高コストである可能性がある。

固定binary slot方式は、private temporary directory内に2つの実行可能regular ELF slotを
一度作り、そのinodeを維持したままA/B内容を交互に上書きする。偶数pairの2-pair blockで
`A@slot0/B@slot1` と `B@slot0/A@slot1` を交差させ、block比の幾何平均
`sqrt(r_even * r_odd)`をbootstrapする。元binary SHA、slot上のSHA、inode/layoutを記録し、
symlink、非regular、非ELF、非executable、setuid/setgid、file capability、
`$ORIGIN`依存RPATH/RUNPATHを拒否する。開始時に元binaryを一度だけsnapshotし、timeoutや
例外ではwrapperだけでなくprocess group全体を停止・回収してからslotを上書きまたは破棄する。

である。observable hashはA/B意味論比較には含むが、独立uncached oracleとは数えていない。
random fixture setupが終局へ到達した場合は、
benchmark corpus生成だけが直前の非終局stateを保持する。これはゲームエンジンの遷移を
変更するものではなく、seed corpusを有限時間で構成するためのharness境界処理である。

instrumentation unitは8 threadからのatomic加算、max、reservation histogram、TT probe
histogram、reset/snapshotを検証した。proof DAG fixtureは37 nodes / 36 edgesで
`complete=true`、`validated=true`、status `proven`、root action `11`だった。

Phase 0の主要計測基盤・fixture・差分検証・sanitizer・allocation/RSS・完走可能なMCTS matrixは完成し、

1. identical `.text` 対照でも一部CIがunityを跨がず、固定slot交差後にもrun間の残留変動がある。
2. kernel policyによりcycles/instructions/cache/branch hardware counterを取得できない。
3. READMEの10,000,000 node exact reveal基準fixtureを基準commitから一意に再現できない。
4. shared/rootの65,536 simulation完走、solverのnoncanonical editor end-to-end、正式 exact TT
   store-event数、solver内部全nodeの手順順序は未取得である。

残存リスクは、microbenchmarkとgprof fallbackが実戦workloadの構成比を完全には表さない
こと、instrumentation ONがparallel scheduleへobserver effectを持つこと、CPU boost下の
微小な残差である。binary-slot crossoverは固定配置バイアスを相殺したが、run間変動を完全には
消していない。compact evidenceの全pairについてslot SHA/inode/layoutと、公開された意味論の
4セル一致を確認済みである。
