# Splendor 2人戦用「めくれ全称分岐つき詰みソルバー」設計仕様書

## 1. 目的

本仕様書は、Splendorの任意局面に対して、指定深さ以内に「何がめくれても勝利が保証される詰み手順」が存在するかを判定するためのソルバー設計を定義する。

用途は、PlayGoの詰碁ランのような反射練習用問題集の自動生成・検証である。

本ソルバーは対局中に毎ターン高速適用するAIではなく、問題生成・検証用の正確性重視の探索器として設計する。

---

## 2. 前提条件

### 2.1 対象ゲーム

- Splendor通常ルールを対象とする。
- 2人戦限定とする。
- 拡張版は対象外とする。
- 伏せ予約は禁止、または詰み問題用ルールとして合法手から除外する。
- 場カードの購入・予約による補充は発生する。
- 補充カードは山札順固定ではなく、未公開カード集合から任意の1枚がめくれるものとして扱う。
- めくれは確率分岐ではなく、全称分岐として扱う。

### 2.2 既存ゲームエンジンの存在

既存のゲームエンジンが以下を提供している前提とする。

- 局面を受け取り合法手リストを返す。
- 合法手を局面に適用できる。
- 宝石取得、予約、購入、返却、貴族獲得、得点計算などのルール処理を行える。
- 終局判定、勝者判定を行える。

ただし、通常のゲームエンジンが山札順固定の補充を前提としている場合、本ソルバー側で「任意めくれ分岐」を扱えるように遷移レイヤーを追加する。

---

## 3. ソルバーが判定する「詰み」の定義

### 3.1 完全詰み

本仕様での詰みは、以下を満たすものとする。

攻撃側が指定深さ以内に勝利できる手順が存在し、かつ、防御側がどの合法手を選んでも、購入・予約後にどの未公開カードがめくれても、攻撃側の勝利が保証される。

形式的には、攻撃側手番では存在量化、防御側手番とめくれでは全称量化を用いる。

```text
攻撃側手番:
  ∃ move . ∀ reveal_outcome . WIN(next_state, depth - 1)

防御側手番:
  ∀ move . ∀ reveal_outcome . WIN(next_state, depth)
```

### 3.2 深さの定義

深さは、攻撃側の着手回数で数える。

- 1手詰め: 攻撃側の次の1手で勝利が保証される。
- 2手詰め: 攻撃側 → 防御側 → 攻撃側で勝利が保証される。
- 3手詰め: 攻撃側 → 防御側 → 攻撃側 → 防御側 → 攻撃側で勝利が保証される。

ソルバーは、呼び出し時に指定された固定深さ `D` に対して、`D` 手以内の完全詰みを判定する。

最短手数を求めたい場合は、呼び出し側が `D = 1, 2, 3, ...` と順に呼び出す。

## 4. 入出力仕様

### 4.1 入力

ソルバーの入力は以下とする。

```text
MateSearchInput
  state: InformationState
  attacker: PlayerId
  max_depth: int
  options: SolverOptions
```

### 4.2 InformationState

山札順を固定しないため、局面は通常の完全順序付き山札状態ではなく、情報局面として扱う。

```text
InformationState
  current_player: PlayerId
  players: PlayerState[2]
  bank_tokens: TokenVector
  visible_cards: VisibleCards
  unseen_cards_by_level: Set<CardId>[3]
  nobles: Set<NobleId>
  final_round_state: FinalRoundState
  other_rule_state: engine-specific
```

重要なのは、山札を順序列ではなく未公開カード集合として持つ点である。

```text
unseen_cards_by_level[level] = まだ公開されておらず、予約も購入もされていないカード集合
```

### 4.3 出力

```text
MateSearchResult
  status: Mate | NoMate | Unknown | InvalidInput
  depth: int | null
  proof_tree: ProofNode | null
  refutation: RefutationNode | null
  stats: SearchStats
```

### 4.4 statusの意味

```text
Mate:
  指定深さ以内に完全詰みが証明された。

NoMate:
  指定深さ以内に完全詰みが存在しないことが証明された。

Unknown:
  探索制限、時間制限、メモリ制限などにより結論が出なかった。

InvalidInput:
  局面がルール上不正、または必要な情報が欠落していた。
```

問題集生成に採用できるのは `Mate` のみとする。

## 5. ルール上考慮すべき要素

### 5.1 宝石

通常のSplendorの宝石を扱う。

```text
白, 青, 緑, 赤, 黒, 金
```

宝石取得後、手元トークンが10個を超える場合は、返却まで含めて1手として扱う。

返却の選択は手番プレイヤーの意思決定であるため、合法手リスト生成時点で、

```text
宝石取得 + 返却パターン
```

を完全な1手として列挙することが望ましい。

既存ゲームエンジンが返却を別フェーズとして扱う場合、ソルバー側では中間状態を残さず、手番終了状態まで正規化して探索する。

### 5.2 カード購入

カード購入時には以下が発生する。

- コスト支払い
- 購入カードのプレイヤー領域への移動
- ボーナス増加
- 得点増加
- 場カード購入の場合、場に空きが出る
- 場に空きが出た場合、同レベルの未公開カード集合から1枚が補充される
- 補充後、貴族獲得判定が発生する

予約済みカードを購入する場合は、場補充は発生しない。

### 5.3 場カード予約

伏せ予約は扱わない。

場カード予約では以下が発生する。

- 場カードをプレイヤーの予約領域へ移動
- 金トークンが銀行にあれば1個獲得
- 手元トークンが10個を超える場合は返却
- 場に空きが出る
- 同レベルの未公開カード集合から1枚が補充される

予約による場補充も、購入と同じく全めくれ分岐として扱う。

### 5.4 予約上限

予約カードは最大3枚とする。

既存ゲームエンジンの合法手生成がこれを保証する前提とする。

### 5.5 貴族

手番終了時に、プレイヤーのボーナスが貴族条件を満たしていれば貴族を獲得する。

同時に複数の貴族条件を満たした場合、通常ルールではそのうち1枚を選んで獲得する。

この選択は手番プレイヤーの意思決定である。

したがって、ソルバーでは以下のどちらかの方式を採用する。

#### 推奨方式: 合法手に貴族選択を含める

```text
購入手 + 補充めくれ + 獲得貴族選択
予約手 + 補充めくれ + 獲得貴族選択
宝石取得手 + 獲得貴族選択
```

を最終的な遷移結果として列挙する。

この場合、探索器は通常の「手」と「めくれ」の分岐だけを扱えばよい。

#### 代替方式: 遷移結果に意思決定分岐を含める

`apply_move` の後に貴族選択分岐を返す。

ただしこの場合、分岐が攻撃側・防御側のどちらの選択かを厳密に扱う必要があるため、実装ミスが起きやすい。

問題生成用の正確性を重視するなら、貴族選択は合法手側に展開する方がよい。

### 5.6 最終ラウンド

通常ルールでは、いずれかのプレイヤーが15点以上に到達した時点で最終ラウンドが開始される。

2人戦では、先後関係により、15点到達後に相手が最後の手番を持つ場合がある。

したがって、ソルバーは「15点到達 = 即勝利」とは扱わず、最終ラウンド終了後の勝者判定を使う。

ただし、局面表現には以下を含める必要がある。

```text
FinalRoundState
  triggered: bool
  trigger_player: PlayerId | null
  remaining_turns: int
```

または既存ゲームエンジンの終局管理情報をそのまま保持する。

### 5.7 勝者判定

最終ラウンド終了後、以下で勝者を判定する。

1. 得点が高いプレイヤーが勝利。
2. 得点同点の場合、購入カード枚数が少ないプレイヤーが勝利。
3. それでも同点の場合は、攻撃側勝利とはみなさない。

問題集用途では、同点・引き分け相当は詰み失敗として扱う。

## 6. めくれ分岐の扱い

### 6.1 めくれが発生する手

めくれ分岐が発生するのは以下である。

```text
場カード購入
場カード予約
```

予約済みカード購入、宝石取得、貴族獲得では場補充は発生しない。

### 6.2 めくれ候補

レベル `L` の場カードが除去された場合、めくれ候補は以下である。

```text
unseen_cards_by_level[L]
```

この集合に含まれる各カードについて、1枚ずつ場に補充した次状態を生成する。

未公開カード集合が空の場合は、補充なしで場スロットを空のままとする。

### 6.3 めくれは全称分岐

めくれはランダムではなく、詰み証明上は全称分岐とする。

攻撃側の手の後でも、防御側の手の後でも、全てのめくれ結果で攻撃側が勝てる必要がある。

```text
ある1枚がめくれた場合だけ負ける
→ 完全詰みではない
```

### 6.4 めくれ後の未公開集合更新

カード `c` がめくれた場合、

```text
visible_cards[L] に c を追加
unseen_cards_by_level[L] から c を削除
```

する。

その後、そのカードが購入・予約されれば、さらに場から消える。

## 7. 探索アルゴリズム

### 7.1 基本構造

本ソルバーは、めくれ全称分岐つきAND-OR探索である。

```text
attacker turn:
  攻撃側は手を選べるため OR ノード。
  ただし、選んだ手の全めくれ結果で勝てなければならない。

defender turn:
  防御側は反証側なので AND ノード。
  防御側の全合法手、かつ各手後の全めくれ結果で勝てなければならない。

reveal:
  めくれは全称分岐。
```

### 7.2 WIN関数

`WIN(state, depth)` は、現在局面から攻撃側が残り `depth` 手以内に完全詰みを達成できるかを返す。

#### 終端条件

```text
終局済み:
  winner == attacker なら True
  それ以外なら False

未終局かつ depth == 0:
  False
```

#### 攻撃側手番

```text
WIN(state, depth):
  current_player == attacker の場合

  ∃ move in LegalMoves(state):
    ∀ next_state in Outcomes(state, move):
      WIN(next_state, depth - 1) == True
```

攻撃側は1手使うため、深さを1減らす。

#### 防御側手番

```text
WIN(state, depth):
  current_player != attacker の場合

  ∀ move in LegalMoves(state):
    ∀ next_state in Outcomes(state, move):
      WIN(next_state, depth) == True
```

防御側の手では、攻撃側の残り手数は減らさない。

### 7.3 Outcomes関数

`Outcomes(state, move)` は、手を適用した後にあり得る全てのめくれ結果、および手番終了処理を含んだ次状態集合を返す。

`Outcomes` は以下を完了した状態だけを返す。

- コスト支払い
- 宝石獲得
- 返却
- 予約
- 購入
- 場補充
- 貴族獲得
- 最終ラウンド状態更新
- 次プレイヤーへの手番移行

探索木に中間状態を残さない。

## 8. 証明木

### 8.1 証明木の目的

ソルバーは単に `Mate` を返すだけでなく、問題集の解説生成に使える証明木を返す。

証明木は、以下を説明できる必要がある。

```text
攻撃側の正解手
めくれごとの対応
防御側の各応手に対する対応
最終的な勝利到達局面
```

### 8.2 証明木ノード

```text
ProofNode
  state_summary
  player_to_move
  chosen_attacker_move: Move | null
  reveal_branches: RevealBranch[]
  defense_branches: DefenseBranch[]
  terminal_result: TerminalResult | null
```

### 8.3 攻撃側ノード

攻撃側ノードでは、詰みを成立させる1つの手を記録する。

```text
AttackerProofNode
  selected_move
  outcomes:
    reveal_card_or_none -> child_proof
```

攻撃側の候補手が複数ある場合でも、証明木には採用した1手だけを保存すればよい。

ただし、問題品質評価のために、詰み初手の数を別途カウントしてもよい。

### 8.4 防御側ノード

防御側ノードでは、防御側の全合法手に対する継続を記録する。

```text
DefenderProofNode
  branches:
    defender_move -> reveal_card_or_none -> child_proof
```

防御側のある手・あるめくれで攻撃側が勝てない場合、その局面は詰み失敗となる。

### 8.5 RefutationNode

詰みなし判定や候補手却下の説明用に、反証ノードを持つとよい。

```text
RefutationNode
  refuting_defender_move: Move | null
  refuting_reveal: CardId | null
  reason: string
  child: RefutationNode | null
```

例:

```text
この攻撃手は、レベル2から赤3点カードがめくれた場合、相手が即購入して15点に到達し、最終ラウンド後に攻撃側が逆転できないため失敗。
```

## 9. メモ化

### 9.1 メモ化キー

山札順を固定しないため、メモ化キーは情報局面に対して作る。

```text
MemoKey
  canonical_information_state_hash
  attacker
  depth
```

`canonical_information_state_hash` には以下を含める。

- 現在手番
- 各プレイヤーの得点
- 各プレイヤーのボーナス
- 各プレイヤーのトークン
- 各プレイヤーの予約カード集合
- 各プレイヤーの購入カード枚数
- 場カード集合
- 未公開カード集合
- 残存貴族集合
- 銀行トークン
- 最終ラウンド状態

### 9.2 正規化

順序に意味がないものはソートしてハッシュ化する。

```text
予約カード集合
購入済みカード集合または購入カードID集合
未公開カード集合
貴族集合
```

場カードについては、スロット位置に意味がない実装なら集合として扱ってよい。

ただし、UI上の位置や補充位置がゲーム状態に影響する実装ならスロット情報も保持する。

### 9.3 単調性の利用

深さに関して次の単調性がある。

```text
depth = d で Mate なら、depth > d でも Mate。
depth = d で NoMate なら、depth < d でも NoMate。
```

したがって、メモ化では以下を保存できる。

```text
proven_mate_min_depth[state]
proven_no_mate_max_depth[state]
```

固定深さのみを使う初期実装では、単純に `(state_hash, depth)` で保存してもよい。

## 10. 探索順序と高速化

本節の最適化は、原則として正確性を落とさないものに限定する。

### 10.1 攻撃側手の順序付け

攻撃側手番では、詰み手が早く見つかるほど探索が減る。

以下の順に合法手を並べる。

1. 最終的に勝利確定に直結する購入
2. 15点以上に到達する購入
3. 貴族獲得を伴う購入
4. 相手の即勝ち候補を予約で消す手
5. 次手に複数の勝ち筋を作る宝石取得
6. 相手の必要宝石を枯らす宝石取得
7. 高得点カード購入
8. その他

これは探索順序の変更であり、合法手自体は削らない。

### 10.2 防御側手の順序付け

防御側手番では、詰みを壊す反証が早く見つかるほど探索が減る。

以下の順に合法手を並べる。

1. 防御側が15点以上に到達する購入
2. 防御側が最終勝利で上回る購入
3. 攻撃側の勝ちカードを予約する手
4. 攻撃側の必要宝石を奪う手
5. 貴族獲得を伴う購入
6. 高得点カード購入
7. 金獲得を伴う予約
8. その他

### 10.3 めくれ候補の順序付け

めくれ候補は、攻撃側にとって危険な順に評価する。

1. 防御側が即購入でき、15点以上に到達するカード
2. 防御側が即購入でき、最終勝利に近づく高得点カード
3. 防御側が購入すると貴族条件を満たすカード
4. 攻撃側の勝ち筋を妨害する予約対象になりうるカード
5. 防御側にだけ有利で攻撃側には不要なカード
6. その他

めくれ分岐は削らない。

危険なものを先に見ることで、詰み失敗の反証を早く見つける。

### 10.4 反証探索

攻撃側の候補手について、まず反証がありそうな分岐から探索する。

反証が見つかった場合、その候補手は即座に却下する。

反証が見つからない場合でも、最終的には全分岐を検証する。

```text
候補手発見・棄却: 高速ヒューリスティック可
Mate判定確定: 全分岐検証必須
```

### 10.5 重複状態の排除

同じ手、同じめくれ、異なる返却・貴族選択などから同一情報局面に到達する場合がある。

`Outcomes` 生成後、canonical hashで重複を除去する。

これは正確性を落とさない。

### 10.6 抽象化の扱い

カード特徴量による抽象化は、候補生成や探索順序付けには使用してよい。

ただし、最終的に `Mate` と判定する前には、カードID単位の全分岐検証を必ず行う。

抽象化だけで詰みありと判定してはならない。

## 11. NoMateとUnknown

### 11.1 NoMate

指定深さ `D` の範囲で、攻撃側の全候補手が、何らかの防御手またはめくれによって反証された場合、`NoMate` とする。

これは、

```text
D手以内の完全詰みは存在しない
```

という意味であり、ゲーム全体で将来的に勝てないことを意味しない。

### 11.2 Unknown

以下の場合は `Unknown` とする。

- 時間制限に到達した。
- メモリ制限に到達した。
- 探索ノード数制限に到達した。
- 既存エンジンが不正状態を返した。
- ルール上未対応の状態が出た。

問題生成用途では、`Unknown` は不採用とする。

## 12. 既存ゲームエンジンとの責務分担

### 12.1 ゲームエンジンの責務

既存ゲームエンジンは以下を担当する。

- 合法手生成
- 手の基本適用
- コスト計算
- 宝石支払い
- 宝石取得
- 返却処理
- 予約上限判定
- 購入可能判定
- 貴族条件判定
- 終局判定
- 勝者判定
- 不正局面チェック

### 12.2 ソルバーの責務

ソルバーは以下を担当する。

- 山札順を持たない情報局面管理
- 場補充時の全めくれ分岐生成
- 攻撃側・防御側・めくれの量化制御
- 深さ管理
- 証明木生成
- 反証ノード生成
- メモ化
- 探索順序付け
- 結果の分類

### 12.3 Adapter層

既存エンジンが順序付き山札を前提にしている場合、Adapter層を設ける。

```text
SolverState
  ↓
EngineState without fixed deck draw
  ↓
legal_moves
  ↓
apply_move_without_draw
  ↓
solver generates all reveal outcomes
```

理想的には、エンジン側に以下の関数を用意する。

```text
apply_move_until_before_refill(state, move)
apply_refill(state, level, card_id | none)
finalize_turn(state)
```

これにより、ソルバーは補充カードだけを差し替えられる。

## 13. 問題品質評価用の追加情報

問題集生成では、`Mate` の有無だけでなく、以下を記録するとよい。

```text
mate_depth
number_of_winning_first_moves
number_of_legal_first_moves
proof_tree_node_count
max_reveal_branch_count
max_defense_branch_count
critical_reveals
critical_defenses
terminal_win_type
```

### 13.1 初手一意性

同じ深さで勝てる初手が複数ある場合、問題としては簡単または曖昧になる。

良問条件として、

```text
number_of_winning_first_moves == 1
```

を重視する。

### 13.2 クリティカルめくれ

以下のようなめくれを `critical_reveal` として記録する。

```text
そのカードがめくれた場合に、攻撃側の応手が変わる
そのカードがめくれた場合に、防御側の最善防御が変わる
そのカードがめくれた場合だけ、証明木が深くなる
```

これにより、人間向け解説で「このめくれにも対応できる」ことを示せる。

### 13.3 勝利タイプ

終端勝利を分類する。

```text
score_win: 得点差で勝利
low_card_tiebreak_win: 同点だが購入枚数差で勝利
noble_win: 貴族獲得が決め手
block_then_win: 相手の即勝ちを防いで勝利
```

## 14. テスト観点

### 14.1 ルール整合性テスト

- 宝石取得後の10枚制限
- 同色2個取得条件
- 金トークン取得条件
- 予約上限3枚
- 予約済みカード購入
- 場カード購入後の補充
- 未公開カード集合が空の場合の補充なし
- 複数貴族候補から1枚選択
- 最終ラウンド開始
- 最終ラウンド終了
- 同点時の購入枚数タイブレーク

### 14.2 めくれ分岐テスト

- レベル1購入時にレベル1未公開カード全てが分岐する。
- レベル2予約時にレベル2未公開カード全てが分岐する。
- 予約済みカード購入ではめくれ分岐しない。
- 未公開集合からめくれたカードが正しく削除される。
- めくれ後の場カード数が正しい。

### 14.3 探索量化テスト

- 攻撃側は1つの勝ち手があれば `Mate` になる。
- 防御側の1つの逃げ手で `NoMate` になる。
- めくれの1つの反例で `NoMate` になる。
- 全めくれで勝てる場合だけ `Mate` になる。

### 14.4 証明木テスト

- `Mate` の場合、全防御手と全めくれに対応する子ノードが存在する。
- `NoMate` の場合、反証手または反証めくれが記録される。
- 終端ノードの勝者が攻撃側である。

## 16. 結論

本ソルバーは、Splendorの2人戦局面に対して、山札順に依存しない完全詰みを判定する。

中心となる考え方は以下である。

```text
攻撃側の手は存在分岐。
防御側の手は全称分岐。
購入・予約後のめくれも全称分岐。
```

したがって、証明された詰みは、

```text
相手がどう受けても、何がめくれても勝てる
```

という強い保証を持つ。

問題集作成では、最終的に全分岐検証を通過した `Mate` 局面のみを採用することで、山札順固定に依存しない実戦的な詰み問題を生成できる。
